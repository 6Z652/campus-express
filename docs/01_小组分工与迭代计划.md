# 小组分工与迭代计划（4 人 · 纵向分工）

> 依据《高级软件工程》项目实践指导书 V6.0 第 1.3 节：**任务分工要按纵向进行，以保证所有学生都能实践完成的需求建模过程**；组长负责报告整理与提交，并在总体评分基础上适当加 2–4 分。
> 提交前请把「成员 A/B/C/D」替换为真实姓名与学号。

## 一、分工总表

| B | √ | √ | √ | √ | √ | √ |
| C | √ | √ | √ | √ | √ | √ |
| D | √ | √ | √ | √ | √ | √ |

**为什么不是横向分工**：若按「一人做需求、一人做设计、一人写代码、一人做测试」切分，只有一人练习建模，直接违背指导书 1.3；纵向切分让 4 人各自完整经历软件工程全生命周期，且便于用 GitHub 提交记录举证。

## 三、迭代计划（10 周 / 5 个 Sprint）

| 迭代 | 周期 | 目标 | 交付物 |
|---|---|---|---|
| S0 | 第 1 周 | 统一环境与协作规范 | 仓库、devcontainer、分支/PR 规范、CI 骨架、调研提纲 |
| S1 | 第 2–3 周 | 业务分析与需求建模 | 业务分析说明书、活动图、业务/系统用例图、4 份用例文档 |
| S2 | 第 4–6 周 | 系统设计与核心编码 | 架构图、分析类图、4 张顺序图、设计类图、数据库设计、4 组 API |
| S3 | 第 7–8 周 | 集成与测试 | 双端界面、单元/功能/兼容性测试、API 文档、缺陷清单 |
| S4 | 第 9–10 周 | 回归、报告与答辩 | 缺陷闭环、全量回归、实践报告、提示词日志、GitHub 记录、演示材料 |

## 四、GitHub 协作约定

- 分支：`main`（受保护）/ `develop` / `feature-UC-01` ～ `feature-UC-04`。
- 每条用例一个 feature 分支、至少一次 PR；PR 需附测试结果截图与 AI 贡献说明，至少一名其他成员 approve 且 CI 全绿才可合并。
- Commit 格式：`<类型>(<用例>): <简述>`，类型取 `feat / fix / test / docs / chore`。
- 所有文档、代码、图表均通过 GitHub 提交；`git log --oneline --graph` 截图作为附录 3 的团队协作佐证。

## 五、每位成员的验收清单

- [ ] 本用例的用例文档（基本流 + 异常流）与系统用例图一致
- [ ] 本用例的顺序图与设计类图中的类名、操作名一致
- [ ] 本用例的后端 API、前端模块、单元测试均已提交且 CI 通过
- [ ] 本用例的 AI 贡献比例、人工修改要点、提示词迭代日志已写入 `docs/`
- [ ] 参与至少 1 次他人 PR 评审，并在 PR 中留下评审意见
- [ ] **7.2 节「AI 辅助开发模式的体会」由本人独立手写 200 字左右**
